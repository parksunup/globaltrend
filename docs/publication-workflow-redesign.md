# 작업자 화면 정리와 발행 절차 간소화 기획안

작성일: 2026-10-19
상태: 전체 개편 기획안. 운영 발행과 병렬로 작성했으며, 등록 자료 선택·일괄 공개와 목록 우선 배치는 1차 개선으로 구현했습니다. 전체 작업 공간 통합과 수정본·공개 취소·휴지통은 후속 범위입니다.

## 1. 무엇을 해결하려는가

사용자님이 지적하신 문제는 발행 과정이 너무 어렵고, 번거롭고, 화면이 어수선하다는 것입니다. 코딩을 모르는 사람이 자료를 선택하고 버튼을 눌러 공개할 수 있어야 합니다. 이미 함께 검토한 내용과 확정한 번역 용어를 다시 처음부터 검수하라고 요구해서도 안 됩니다.

이번 작업은 단순히 버튼 이름을 바꾸는 일이 아닙니다. 제출 자료를 보는 곳과 실제 공개하는 곳을 하나의 작업 흐름으로 연결하고, 내부 처리 단계를 사용자가 일일이 수행하지 않도록 만드는 일입니다.

확정된 요구사항은 다음과 같습니다.

- 관리자와 편집자 모두 자료를 수정·삭제할 수 있습니다. 삭제 권한을 익명 방문자에게 주는 것은 아닙니다.
- 최종 공개 여부는 총괄 관리자가 결정합니다.
- 검수자와 검수일은 내부 기록으로 남기고 공개 화면에는 표시하지 않습니다.
- 사용자가 이미 수행한 검수를 그대로 이어받습니다. 다만 용어 기준의 확정과 법률 전문 모든 문장의 정확성 검증을 같은 것으로 기록하지 않습니다.
- 자동 검사 결과를 사람의 검수 결과로 둔갑시키지 않습니다.
- 발행할 자료를 여러 개 선택하고 한 번의 발행 동작으로 공개할 수 있게 합니다.
- 기존 공개 화면의 밝은 테마·어두운 테마 및 자료 내용은 유지하면서 작업자 화면을 정리합니다.

## 2. 현재 코드에서 확인한 문제

아래는 저장소 코드를 읽고 확인한 사실입니다. 이 문서 작성 과정에서 운영 계정으로 실제 발행·수정·삭제를 실행하지 않았습니다. 부모 작업에서 진행하는 운영 발행과 이 기획안의 구현 완료를 혼동하지 않습니다.

| 현재 경로·코드 | 확인된 동작 | 사용자가 겪는 문제 |
| --- | --- | --- |
| `/` · `app/page.tsx` | `SITE_ENTRY=public`이면 공개 홈, 그 외에는 제출물 검토 보드가 나옵니다. | 같은 주소의 역할이 설정에 따라 바뀝니다. 작업자 홈이라는 이름이 실제 쓰기 화면을 뜻하지 않습니다. |
| `/team` · `app/team/page.tsx` | 로그인 없이 읽는 `ReviewShell`입니다. 실제 자료 편집·발행 화면이 아닙니다. | 화면은 검수 보드처럼 보이는데 실행 버튼은 사용할 수 없습니다. |
| `app/components/review-shell.tsx` | 출처·법제 목록·비교 기준을 고르고, PR 제출물도 다른 모드로 봅니다. `/work`와 `/work/legal` 링크는 사이드바 아래에 있습니다. | 실제로 해야 할 동향·법제 작업보다 설정 성격의 목록과 PR라는 개발 용어가 먼저 나옵니다. |
| `/work` · `app/work/page.tsx` | 로그인 아래에 수집 상태, 제출 자료 선택, 긴 새 초안 입력창, 등록 동향 목록이 이어집니다. | 발행할 자료를 보려면 긴 화면을 내려가야 합니다. 새 글 작성과 발행 대기 자료 처리가 뒤섞여 있습니다. |

| `/legal-drafts` · `app/components/public-draft-viewer.tsx` | 별도 초안 보기이며 “사람 검수 미착수” 문구가 고정돼 있습니다. | 실제 검수 이력과 화면 설명이 어긋날 수 있습니다. |
| `app/components/submission-preview.tsx` | PR 파일 표시와 피드백이 중심이며 고정된 “검수 전 초안” 문구도 있습니다. | 의견을 남기거나 함께 내용을 확인해도 발행 상태나 검수 이력과 이어지지 않습니다. |
| 여러 작성 액션 | 실패 시 “입력 내용과 권한”, “마이그레이션·권한·현재 상태” 같은 포괄적인 설명으로 돌아옵니다. | 사용자가 무엇을 고쳐야 하는지 알 수 없습니다. 개발 용어를 알아야 대응할 수 있습니다. |

핵심은 세 가지입니다. 자료를 보는 곳과 공개하는 곳이 떨어져 있고, 내부 상태 변경을 사람이 대신 눌러 주며, 자료 상태를 실제 기록 대신 고정 문구로 설명합니다.

## 3. 제안: 작업은 `/work` 한 곳에서 시작

작업자 홈은 `/work`로 통일합니다. 첫 화면의 핵심 질문은 “지금 무엇을 공개할까요?”입니다. 출처 설정, 수집기 로그, 기술 정보, GitHub 제출 정보는 필요한 경우에만 펼칩니다.

주 메뉴는 네 개로 줄입니다.

1. **자료 관리**: 동향·법제를 검색하고 선택해서 공개하거나 수정합니다. 로그인 후 기본 화면입니다.
2. **주간호**: 동향을 골라 주간호를 구성합니다. 개별 동향 공개와 주간호 포함 여부는 구분합니다.
3. **수집 상태**: 수집 성공·실패와 확인이 필요한 원문을 봅니다.
4. **도움말**: 팀 가이드와 작업 방법을 봅니다.

상단에는 “공개 사이트 보기”, 계정, 로그아웃만 둡니다. 자료 유형과 상태는 본문 필터로 둡니다. 여러 기능을 같은 크기의 카드로 늘어놓지 않습니다.

`/`의 공개·작업자 우선순위를 지금 바꾸지는 않습니다. 어떤 진입 설정이든 “작업 공간” 링크는 항상 `/work`를 가리킵니다. 훗날 공개 홈을 기본으로 바꾸더라도 작업자 주소는 유지됩니다.

### 기존 주소 처리

- `/work/legal`: 법제 필터가 선택된 자료 관리 화면으로 연결합니다. 기존 상세 주소는 유지하거나 대응 상세로 이동시킵니다.
- `/team`: 기존의 공개 열람 범위를 유지하는 제출 자료 열람 화면으로 남깁니다. 로그인해야만 가능한 편집 화면과 구분하고 “편집하려면 작업 공간으로”를 표시합니다.
- `/legal-drafts`, `/legal-translation`: 이미 공유한 자료 열람 링크는 유지합니다. 로그인한 작업자는 해당 자료의 편집 화면으로 바로 이동할 수 있습니다.
- `/public` 이하: 발행된 자료를 읽는 공개 페이지입니다. 미발행 DB 초안이 섞이지 않도록 합니다.
- PR Preview: 상단에 “화면 확인용 · 실제 사이트에는 저장하지 않습니다”를 한 번 표시합니다. 저장이 막혀 있을 때 “운영 작업 공간 열기”를 제공합니다. 운영에서는 같은 경고를 표시하지 않습니다.

## 4. 자료 목록: 자료 하나는 목록 한 줄

동향과 법제를 같은 관리 틀에서 다루되 내용 편집기는 각각에 맞춥니다. 법제는 번역 전문과 17개 비교표를 함께 가진 판본 하나가 발행 단위입니다. 비교셀 119개를 사람이 하나씩 발행하게 만들지 않습니다.

목록의 기본 정보는 제목, 유형·국가, 현재 상태, 필요한 조치입니다. 원문 주소·판본 해시·내부 ID·원문 전체·수집기 로그는 상세로 옮깁니다.

상태는 사용자에게 다음 네 가지로 보여 줍니다.

| 표시 | 뜻 | 기본 동작 |
| --- | --- | --- |
| 작성 중 | 내용이 저장됐으며 공개할 준비를 하는 자료입니다. | 내용 열기 |
| 공개 준비 | 필수 정보가 갖춰졌고 관리자에게 공개를 요청할 수 있습니다. | 관리자는 공개하기 |
| 수정 필요 | 누락·충돌 등 구체적으로 해결할 문제가 있습니다. | 문제 확인 |
| 공개 중 | 현재 공개 사이트에 보이는 판본입니다. | 공개 화면 보기 |

“검토 기록 있음”은 상세의 내부 정보입니다. 이것을 다섯 번째 진행 단계로 만들어 매번 눌러야 하는 절차로 추가하지 않습니다. 기존 내부 상태값이 더 많더라도 화면에서는 중복 단계를 합칩니다.

전체 선택은 현재 검색·필터 결과에 적용합니다. 페이지가 나뉜 경우에는 “이 페이지 20건 선택”과 “검색 결과 전체 58건 선택”을 명확히 구분합니다. 실제 건수는 DB 응답으로 계산하며 예시 숫자를 하드코딩하지 않습니다.

## 5. 발행: 자료 선택 → ‘선택한 N건 공개’

일상 발행에서 사람에게 요구하는 동작은 자료 선택과 발행 버튼입니다.

1. 시스템이 제목·내용·원문 연결·판본 변경 여부·자료 누락을 자동 확인합니다. 검사 결과는 목록에 미리 표시합니다.
2. 총괄 관리자가 한 건 또는 여러 건을 선택합니다. 상세 확인은 원하실 때 열 수 있습니다.
3. 하단 고정 영역의 **“선택한 N건 공개”**를 누릅니다.
4. 서버가 필요한 자료 등록과 내부 상태 전환을 처리하고, 공개 결과를 같은 화면에 표시합니다. 사용자가 등록·검수 요청·승인 버튼을 차례로 누르지 않습니다.
5. 성공한 자료 옆에 “공개 화면 보기”가 나타납니다. 목록 선택은 성공한 자료에서 해제합니다.

별도 확인 모달이나 모든 자료의 원문 열람 여부 체크는 기본으로 요구하지 않습니다. 발행 버튼의 문구와 선택 수가 명확한 의사 표현입니다. 관리자 여부는 서버에서도 검사합니다.

자동 검사는 자료가 실질적으로 정확하다는 보증이 아닙니다. 하지만 이 설명을 매 항목마다 긴 경고나 확인 체크로 반복하지 않습니다. 운영 규칙과 도움말에 설명하고, 실제 문제가 있는 자료에만 구체적인 이유를 표시합니다.

### 이미 검토한 자료

현재 함께 검토한 자료와 사용자님이 확정하신 번역 용어는 검토 이력으로 등록합니다. 실제 검토 범위·대상 판본·기준 문서를 내부에 연결합니다. 날짜를 과거로 추측해 만들거나, 용어만 확정한 것을 모든 법조항의 법적 정확성 승인으로 확대하지 않습니다.

관리자가 이번에 공개를 지시한 대상에 대해 발행 결정을 저장합니다. 이미 끝난 검토를 다시 하도록 요구하거나 새로운 항목별 확인 체크를 만들지 않습니다.

향후 자료가 수정되면 기존 판본의 검토 이력은 보존하고 “검토 후 변경된 내용”을 내부에 보여 줍니다. 전체 자료를 다시 읽었다는 선언을 강제하지 않습니다. 관리자는 변경 부분을 보고 새 판본을 공개할 수 있습니다.

### 일괄 발행의 실패 처리

- **사전 검사에서 문제 발견**: 문제 있는 자료만 선택 불가로 표시하고 그 줄에 해결 방법을 적습니다. “내용이 비어 있습니다. 내용 추가”처럼 안내합니다. 나머지 자료 공개는 가능합니다.
- **자료가 다른 사람에 의해 바뀜**: 해당 자료는 공개하지 않고 “선택한 뒤 내용이 바뀌었습니다. 바뀐 내용 보기”를 표시합니다. 최신 내용으로 몰래 교체해 발행하지 않습니다.
- **처리 도중 일부 실패**: “18건 공개됨 · 2건 처리하지 못함”과 실패한 제목을 표시합니다. 성공한 자료를 다시 공개하지 않고 “실패한 2건 다시 시도”를 제공합니다.
- **재시도·연속 클릭**: 서버가 동일 판본의 발행을 중복 생성하지 않습니다. 처리 중에는 버튼에 진행 상태를 표시합니다.
- **법제 한 판본**: 번역 전문·비교표·공개 판본 연결을 한 묶음으로 처리합니다. 전문만 바뀌고 비교표는 구판으로 남는 부분 성공은 허용하지 않습니다.
- **법제 전문이나 비교 내용 일부 없음**: 실제 공개 가능한 범위를 정확히 표시합니다. “전문 없음 · 비교표만 있음”처럼 알리고, 부분 공개를 의도적으로 선택할 수 있게 합니다. 누락된 자료를 완성본이라고 표시하지 않습니다.
- **연결 실패**: 상태가 확인되지 않으면 성공했다고 표시하지 않습니다. 다시 조회하여 실제 결과를 보여 줍니다.
- **DB 기능 미적용**: 입력 내용을 보존하고 “발행 기능이 아직 준비되지 않았습니다. 자료는 보관돼 있습니다”로 안내합니다. 원인과 기술 정보는 관리용 상세에 둡니다.

## 6. 수정·삭제·공개 취소

팀원도 수정·삭제할 수 있다는 사용자님의 지시를 반영합니다. 공개 방문자에게 편집 권한을 주지 않습니다. 최종 발행은 관리자만 실행합니다.

- **작성 중 자료 수정**: 팀원이 바로 수정하고 저장합니다.
- **공개 중 자료 수정**: 공개본은 그대로 두고 수정본을 저장합니다. 관리자에게 “수정본 공개” 버튼이 나타납니다. 저장만으로 공개본이 바뀌지 않습니다.
- **새 판본 공개**: 이전 공개본을 내부 이력에 보관하고 새 내용으로 교체합니다. 공개 주소는 가능한 한 유지합니다.
- **공개 취소**: 관리자가 실행하면 공개 목록·검색·상세에서 내려갑니다. 작업 공간에는 자료와 이력이 남습니다. 안내는 “공개를 취소했습니다. 자료는 작업 공간에 남아 있습니다”입니다.
- **삭제**: 관리자·편집자 모두 휴지통으로 이동할 수 있습니다. 기본 삭제는 복구 가능한 삭제로 만듭니다. 공개 중 자료는 먼저 공개 취소가 필요하다는 상태와 관리자에게 요청하는 버튼을 보여 줍니다. 팀원 삭제 권한과 최종 공개 결정이 충돌하지 않게 합니다.
- **영구 삭제**: 일상 작업 화면의 기본 버튼에 넣지 않습니다. 휴지통의 별도 기능으로 다룹니다.

공개 취소와 삭제처럼 실제 노출이나 보관 상태를 되돌리는 동작에는 대상 수와 결과를 짧게 확인합니다. 평상시 공개는 매번 확인 모달을 추가하지 않습니다.

## 7. 구체적인 화면안

아래 숫자와 제목은 화면 구성을 설명하기 위한 예시입니다. 운영 현황을 뜻하지 않습니다.

### A. 작업자 홈

```text
GlobalTrend 작업 공간                 공개 사이트 보기   내 계정

자료 관리    주간호    수집 상태    도움말

자료 관리                                    [+ 새 자료]

[전체] [동향] [법제]        [제목·국가로 검색                 ]
[전체 상태 ▾]  [공개 준비만]  [수정 필요한 자료]

□ 이 페이지 전체 선택

선택  자료                                  상태        할 일
□     EDPB, 개인정보 처리 지침 발표          공개 준비   [내용 보기]

□     OECD, 신경 데이터 정책 보고서          수정 필요   [누락 내용 보기]

─────────────────────────────────────────────────────────────────
2건 선택됨      [선택 해제]                     [선택한 2건 공개]
```

편집자 계정에서는 마지막 버튼을 “관리자에게 공개 요청”으로 보여 줍니다. 관리자는 같은 목록에서 바로 공개합니다. 긴 입력 폼은 첫 화면에 펼쳐 놓지 않습니다.

## 8. 시각 디자인 정리 원칙

- 공개 사이트의 글꼴과 색상 기준을 재사용합니다. 밝은·어두운 테마 모두 같은 작업 구조를 제공합니다.
- 작업자 화면은 읽기와 조작이 중심이므로 지구·책 같은 큰 장식 이미지를 배치하지 않습니다.
- 제목은 26~30px, 목록 제목은 17~18px, 본문·버튼은 16px를 시작점으로 실제 화면에서 확인합니다. 긴 법제 본문은 줄 길이와 행간을 확보합니다.
- 기본 행동은 화면당 하나로 강조합니다. 목록에서는 선택 자료 공개, 상세에서는 해당 자료 공개 또는 수정본 공개입니다.
- 표의 모든 칸을 카드로 쪼개지 않고 한 줄에서 제목·상태·동작을 훑어볼 수 있게 합니다.
- 수집기 실패 로그, 출처 설정, PR 커밋, 원문 해시는 접을 수 있는 내부 상세로 옮깁니다.
- 휴대전화에서는 각 행을 간단한 목록으로 바꾸고 선택 수와 공개 버튼을 하단에 고정합니다. 키보드 선택, 체크박스 라벨, 처리 결과 읽기도 지원합니다.

## 9. 구현 순서와 완료 기준

### 먼저: 현재 공개 요청 마무리

현재 부모 작업에서 진행 중인 운영 DB 적용, 검수 이력 반영, 자료 발행을 이 화면 개편 때문에 지연하지 않습니다. 이 기획안은 기존 공개 작업을 대체하지 않습니다.

### 1차: 실제 클릭 수 줄이기

- `/work`에 동향·법제 통합 목록, 유형·상태 필터, 다중 선택을 만듭니다.
- 제출 자료를 목록에서 선택하면 서버가 등록하고 공개까지 이어가는 동작을 만듭니다. 동향 후보는 주간 예시호만이 아니라 전체 실제 편집 자료를 읽습니다.
- 관리자 일괄 발행, 편집자 공개 요청, 자료별 성공·실패 결과를 연결합니다.
- 기존 검수 기록을 실제 자료 판본과 연결하고 고정된 미검수 문구를 제거합니다.
- 검수자·검수일은 내부 상세에서만 확인합니다.
- `/work/legal`과 기존 작업 링크를 새 목록으로 연결합니다.

**완료 기준:** 관리자가 목록에서 동향 3건과 법제 1건을 선택해 한 번 발행하면, 각각 공개 동향·검색·법제 전문·비교표에 나타납니다. 매 건 등록·승인·발행 버튼을 따로 누르지 않습니다. 이미 검토한 자료에 재검수 체크를 요구하지 않습니다.

### 2차: 운영하면서 고칠 수 있게 만들기

- 공개본을 유지하면서 수정본 저장·변경 비교·수정본 발행을 연결합니다.
- 공개 취소, 휴지통, 복원을 연결합니다.
- 팀원의 수정·삭제 권한과 관리자의 최종 발행 권한을 실제 서버에서 검증합니다.
- 동시 수정·중복 클릭·일부 실패와 재시도를 처리합니다.

**완료 기준:** 팀원이 오탈자를 수정해도 승인되지 않은 변경이 공개본을 바로 덮지 않습니다. 관리자가 수정본을 공개하거나 공개를 취소할 수 있고, 실패한 자료만 다시 시도할 수 있습니다.

### 3차: 주간호 작업 연결

- 공개된 동향과 공개 준비 자료를 함께 고르고 주간호 순서·목차를 정합니다.
- “주간호 공개”가 선택 동향의 공개를 필요로 한다면 처리 대상을 명확히 보여 주고 한 흐름으로 실행합니다.
- 동향 자체의 발행 상태와 주간호의 발행 상태를 구분합니다. 특정 주간호에 넣지 않은 동향도 개별 공개할 수 있습니다.

## 10. 구현 때 반드시 확인할 사례

- 관리자에게는 공개 버튼, 편집자에게는 공개 요청 버튼이 보이고 서버 권한도 일치하는가.
- 익명 방문자는 목록 열람 범위만 접근하고 수정·삭제·발행할 수 없는가.
- 기존 검토 이력이 있는 자료에 일괄 발행이 추가 검수 체크를 요구하지 않는가.
- 새로 바뀐 자료를 오래된 판본으로 발행하려 할 때 해당 자료만 멈추는가.
- 번역 전문과 17개 비교 내용이 동일 판본으로 공개되는가.
- 동향 전체 편집 자료가 목록에 나타나며 주간 예시호 7건에만 묶이지 않는가.
- 일부 실패 후 재시도해도 성공한 자료가 중복 생성되지 않는가.
- 공개 취소한 자료가 목록·검색·상세·연결된 법제 보기에서 내려가는가.
- 공개본의 수정 저장이 즉시 노출되지 않고, 수정본 공개 때 실제 화면에 반영되는가.
- 검수자·검수일이 공개 HTML이나 공개 응답에 불필요하게 포함되지 않는가.
- Preview에서 운영 데이터를 바꾸지 않으며, 운영 작업 공간으로 이동하는 방법은 분명한가.
- 작은 화면과 키보드만으로도 자료 선택·결과 확인을 할 수 있는가.

이 문서는 현재 UI 변경을 구현했다는 보고서가 아닙니다. 실제 코드에서 확인한 문제를 바탕으로 다음 작업의 화면 구성과 동작을 구체화한 기획안입니다.
