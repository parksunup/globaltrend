## 새 작업에서 공식 사이트·현재 파서를 재검증한 결과 — 2026-10-13

PR #32와 `codex/trend-collector-cloud`의 기존 설계·계획을 이어서 진행했습니다. 이전 작업의 CONNECT 403 기록은 과거 결과입니다. 이번 작업의 `/etc/codex/network-policy.json`은 `unrestricted`였고, 환경 상태 도구의 네트워크 적용 상태는 `unknown`이었습니다. 실제 요청을 별도로 시험했으며 네트워크 설정·요금제는 변경하지 않았습니다.

- 설정된 9개 공식 목록 URL의 직접 HTTPS GET은 모두 HTTP 200입니다. 기존 robots-aware 진단도 목록/조사 표본 18개를 모두 읽었습니다. 이전 프록시 거부는 이번 요청에서 재현되지 않았습니다.

- 9곳 모두 현재 목록과 첫 문서를 해석했습니다. ICO/PDPC의 실제 1→2페이지에서 서로 다른 결과와 다음 페이지 정보를 확인했습니다. 표본 진단이므로 전 기간·전체 문서·다른 템플릿까지 검증한 것은 아닙니다.

- ICO의 현재 공개 페이지가 쓰는 내부 `/api/search` 요청과 명시적 페이지 정보를 사용합니다. PDPC도 현재 페이지의 `/api/listing-api` 응답을 사용하고, 본문은 페이지에 포함된 RSC의 실제 기사 `content`를 읽습니다. **공식 지원 API가 아닙니다.** 예상한 DOM·JSON·UTF-8 길이 구분 형식이 바뀌거나 참조가 풀리지 않으면 실패합니다. JavaScript·추적 코드·CAPTCHA는 실행하지 않습니다.
- OECD 표본은 표시 날짜 `6 October 2026`과 `datetime=2026-10-05`가 달라 게시일 `null`입니다. PPC 표본은 발표일과 게시일 의미가 섞이고 연결 자료가 미열람이므로 날짜/전문 확인을 보류합니다.
- 9개 출처 모두 `enabled=false`, 수집·저장·AI 승인 false를 유지했습니다. 진단 결과는 `held / coverage_complete=false`이며 DB 쓰기·한국어 초안·발행 성공으로 표시하지 않습니다. main 병합·정기 실행 활성화·추가 유료 서비스 도입은 하지 않았습니다.

- 실제 HTML 다음 링크 또는 검증한 ICO/PDPC JSON 페이지 정보 순회, 페이지·문서 상한, 페이지 내용 지문과 다음 항목 위치를 저장하는 제한적 소급 재시작. 목록 정렬이 바뀌면 해당 페이지를 다시 확인합니다. 첫 페이지/RSS만 본 범위는 완전 수집으로 표시하지 않습니다.

- TLS/프록시 유지, 실제 robots 정책과 Crawl-delay, 요청 20초·응답 2 MB·실행 전체 요청 최대 100회/10분·최대 3회 재시도·Retry-After 최대 60초. PDF 텍스트 추출은 최대 50쪽이며 빈/OCR 필요/잘못된 PDF는 실패입니다.
- ICO/PDPC에서 반복 목록·중복 항목을 감지하면 실패하며 체크포인트를 전진시키지 않습니다. 리디렉션은 최대 5회이고 각 요청에서 공식 호스트·robots·간격·공유 요청/시간 예산을 다시 적용합니다.
- 본문 최대 80,000자. 그보다 긴 문서는 조각별 독해를 아직 구현하지 않아 보류하며 일부를 전문처럼 저장하지 않습니다. 원문/PDF 응답 파일은 영구 보관하지 않습니다.
- 기존 `ingest_source_item`의 중복 방지·판본·draft_jobs를 그대로 사용합니다. 저장 실패/용량 중단 뒤 다른 쓰기를 다시 시도하지 않습니다. 오류가 난 실행은 성공으로 기록하지 않습니다.
- DB claim: 한 작업 한 실행, 임대 30분, 임대 만료 재시도, 최대 3회 시도, 한국시간 하루 총 claim 최대 10회(재시도 포함).
- submit: 정확한 작업·임대·판본·지침·출처 승인 재확인, 실제 판본에 존재하는 인용·핵심 내용의 근거 인덱스 확인. **구조/인용 일치 검사는 내용 정확성을 승인한 것이 아닙니다.**
- 새 초안은 reports의 `draft`, `human_reviewed=false`로만 저장합니다. 기존 보고서가 있으면 자동 덮어쓰기 대신 `proposed_draft`로 사람 검토에 남깁니다. 구판 submit은 cancelled 처리합니다.
- 기존 `/work`에 DB 수집 대기함·원문 판본·짧은 요약·상세·핵심·시사점·근거·미열람 링크·작업 상태를 추가했습니다. 검수자는 앱 로그인만 필요하고 Supabase 관리자 권한은 필요 없습니다. DB 수정 후 새로고침하면 커밋·배포 없이 갱신됩니다.
- 기존 자연어 피드백은 `collector-data` 범위와 자료/원문 판본 ID로 연결합니다. 앱 커밋은 실제 `VERCEL_GIT_COMMIT_SHA`를 사용합니다. 공개 피드백에는 원문/초안을 복사하지 않으며 공개 메뉴에 피드백 항목을 추가하지 않았습니다.
- 익명 원문/초안 조회와 브라우저의 worker submit은 거부합니다. 권한 있는 조회 본체는 private schema에 두고 public에는 권한을 높이지 않는 입구만 둡니다.

## 실제 검증과 하지 못한 검증

- 이번 작업: Python 회귀 검사 46개, 기존 앱 검사 28개, TypeScript, 팀 자료 검사, 웹 빌드 통과. 독립 리뷰에서 재현한 반복 목록의 잘못된 완전 성공과 리디렉션의 robots/요청 예산 누락을 RED→GREEN 검사로 수정했습니다.
- 아래 합성/로컬 DB 검사 결과는 이전 PR 단계의 기록입니다. 이번 운영 1건 시험은 DB 구조·검수 화면 코드를 변경하지 않고 기존 RPC와 배포를 사용했으며, 결과는 위 별도 절과 1건 시험 문서에 기록했습니다.
- 실제 로컬 PostgreSQL에서 수집/판본/권한/발행 기존 검사와 신규 22개 pgTAP 검사 통과. 서로 다른 두 DB 연결의 동시 claim 결과는 `[1,0]`으로 중복이 없었습니다.
- 로컬 합성 자료: worker 초안 저장 → 검수자 앱 로그인 → DB 원문/초안/근거 표시 → DB 제목 변경 후 같은 빌드 새로고침으로 갱신 → null 핵심 내용에도 화면 유지 → 공개 화면에서 미승인 자료 미노출. 브라우저 콘솔 오류 없음.
- 합성 자료는 실제 EDPB 발표가 아니며 테스트 링크는 example.test입니다. 운영 DB에는 이 합성 자료를 넣지 않았습니다.
- 운영 Supabase의 기존 발행 보호 migration과 신규 작업관리/private 조회 migration을 적용했습니다. 운영 원문·초안은 0건 유지합니다. 용량·팀 조회·익명/worker 권한 차단을 실제 SQL로 확인했습니다.
- 1회 클라우드 연결 시험이 2026-10-13 10:52:40 한국시간에 실제 실행 요청으로 전달됐습니다. GitHub README 읽기, Supabase 출처 3건 SELECT와 0건 UPDATE/ROLLBACK을 확인했습니다. 현재 1회 작업은 완료/비활성, 다음 실행 없음입니다. 정기 초안 작업을 만들지는 않았습니다.

## 실행 방법과 예약 상태

```bash
python -m pip install -r scripts/collector/requirements.txt
python -m unittest discover -s tests -p 'test_collector*.py'
python -m scripts.collector.run --output work/collector-result.json
python -m scripts.collector.run --probe --output work/collector-probe.json
```

기본은 dry-run이며 미승인 출처는 네트워크/DB를 호출하지 않습니다. 진단용 `--probe`는 robots와 현재 목록/첫 발견 문서만 제한적으로 읽어 실제 파서를 검사하고 DB에 저장하지 않습니다. 목록 발견이 실패했을 때만 조사 표본으로 상세 진단을 이어가며, 목록 실패 자체는 실패로 남깁니다. 단일 표본의 본문 해석 성공은 출처 승인이나 내용 정확성에 대한 사람 승인과 다릅니다. `--write`에는 서버 비밀 설정과 `COLLECTION_ENABLED=true`, `FREE_LIMITS_VERIFIED=true`, `CLOUD_PIPELINE_VERIFIED=true`, 출처별 승인 설정이 모두 필요합니다. 이것은 검증 결과를 대신하는 버튼이 아닙니다. 실제 증거를 확인하기 전 true로 설정하면 안 됩니다.

수집 workflow는 수동 실행과 **기본 차단된 정기 실행 정의**를 제공합니다. cron은 `17 22 * * *`(UTC, 다음 날 한국시간 07:17)이며 schedule 이벤트는 `SCHEDULE_ENABLED`와 기존 운영/무료/연결 gate를 모두 통과해야 job을 시작합니다. GitHub 정기 실행은 기본 브랜치의 workflow로 실행되므로 PR 브랜치의 설정 준비가 실제 활성화를 뜻하지 않습니다. 사용자 지시에 따라 main 병합·정기 활성화는 하지 않았습니다. 시간은 지연/누락될 수 있어 정확한 한 시간 완료에 의존하지 않습니다.

초안 작성 지침은 [초안 편집 실행 지침 v1](./trend-draft-worker.md)에 있습니다. 초안 08:17 KST 반복 예약은 미생성입니다. 준비된 job만 claim하며 수집이 늦으면 다음 실행에 남깁니다. 초기 하루 10건 한도는 DB에서도 강제합니다. 이 대화의 전체 구현 작업을 1회 예약 시험의 범위로 바꾸지 않아야 합니다.

소급 예시(활성화 조건을 실제로 충족한 뒤에만):

```bash
python -m scripts.collector.run --write --source edpb --since 2026-10-01 --until 2026-10-03 --max-pages 2 --max-items 10
```

먼저 작은 범위로 검사합니다. 같은 범위를 다시 실행하면 저장된 위치부터 이어가며, URL/본문 해시 중복은 기존 DB가 막습니다. 실패한 상세는 발견 기록으로 남습니다. 자료가 없던 성공과 실패를 구분합니다.

## 비용: 확인한 근거와 아직 확인 못한 값

- [GitHub의 현행 공식 문서 원본](https://raw.githubusercontent.com/github/docs/main/content/billing/concepts/product-billing/github-actions.md)을 실제 읽었습니다. 공개 저장소의 표준 hosted runner 실행은 무료입니다. 현재 저장소 visibility는 public이며 수집 workflow는 ubuntu-latest입니다. 대형 runner를 사용하지 않습니다.
- 결과 artifact 업로드와 pip cache를 새 수집 workflow에서 제거했습니다. 파일/캐시 저장 무료 잔량을 추정해 과금되는 저장 기능을 켜지 않습니다. 짧은 작업 요약과, 쓰기 모드에서는 DB 실행 기록만 남깁니다. 기존 CI 설정은 별개입니다.
- Supabase 조직의 실제 plan/tier는 free/tier_free입니다. 최신 프로젝트 DB RPC 측정값은 약 13.35 MB이며, 코드/DB가 400,000,000바이트에서 수집·초안 쓰기를 중단합니다. [공식 DB 크기 문서](https://supabase.com/docs/guides/platform/database-size)는 Free 500 MB 초과 시 읽기 전용 전환을 설명합니다.
- [공식 전송량 문서](https://supabase.com/docs/guides/platform/manage-your-usage/egress)는 Free의 uncached/cached 각 5 GB와 유료 계획의 초과 요금 구분을 설명합니다. 자동 도구로 월 전송량을 조회하지는 못했습니다. 후속 1건 시험 도중 사용자가 제공한 현재 Usage 화면은 Free Plan·한도 미초과·Egress 0.003/5 GB·Cached Egress 0/5 GB입니다. 실시간 자동 잔량 조회나 반복 운영의 보장은 아닙니다. 새로운 유료 프로젝트·요금제·저장 add-on은 만들지 않았습니다.
- [OpenAI 공식 Codex README](https://github.com/openai/codex#using-codex-with-your-chatgpt-plan)는 ChatGPT 로그인으로 포함된 구독을 사용하는 경로를 설명합니다. 별도 OpenAI API 키·유료 AI SDK 호출 코드가 없습니다. **이 계정의 정확한 구독 유형·남은 사용량·예약 사용 한도는 도구가 제공하지 않아 확인하지 못했습니다.** API 사용 요금이 없다는 것과 기존 구독 사용량을 소비하지 않는 것은 다릅니다.
- Vercel의 현재 계정 요금제/배포·전송 잔량은 연결 도구의 응답으로 확인되지 않았습니다. 기존 프로젝트와 Git Preview 연동만 사용하며 새 호스팅 서비스/유료 옵션을 추가하지 않습니다. 무료 한도 오류가 나오면 재시도 폭주/업그레이드 대신 중단합니다.
- 따라서 **추가 비용 없는 완전 자동 운영을 확인했다고 할 수 없습니다.** 자동 충전·유료 전환·초과 결제 코드는 없고, 확인되지 않은 운영/비용/연결 조건은 기본 중단입니다.

## 프로젝트 리드와 담당자의 다음 확인

1. 이번 환경에서는 9개 공식 사이트의 접근과 한정된 현재 파서 시험을 통과했습니다. 이전 CONNECT 403 때문에 네트워크 설정을 다시 바꿀 필요는 없습니다. 다른 작업에서는 그 작업에 실제 적용된 정책을 확인합니다. 원문 리디렉션/첨부가 새로운 호스트를 요구하면 실제 링크와 정책을 확인한 뒤 추가합니다. 정책·요금·운영 확인용 사이트와 실제 Supabase/Preview 호스트의 접근은 별도입니다. 차단 우회나 TLS 해제는 하지 않습니다.
2. Supabase 조직의 현재 Usage 화면은 사용자가 제공해 1건 시험에 확인했습니다. 반복 운영 전에는 필요하면 갱신된 사용량을 확인합니다. GitHub 개인 **Settings → Billing and licensing**에서 유료 초과 지출 차단, Vercel 팀의 **Settings → Billing**에서 현재 요금제/사용량, ChatGPT/Codex의 사용량 화면에서 구독 잔량을 확인해 주세요. 세부 메뉴 이름은 서비스 UI 개편에 따라 달라질 수 있습니다. 비밀키를 대화에 보내실 필요는 없습니다.
3. 동향 담당자가 기관별 수집·저장·AI 처리·번역/요약·공개 조건, 날짜 근거, 실제 목록 순회와 미열람 문서를 확인합니다. 9곳은 조사 후보이며 이미 승인된 운영 출처가 아닙니다.
4. 실제 EDPB 원문 1건의 운영 DB→한국어 미검수 초안→배포 검수 화면 시험은 완료했습니다. 처리량·출처 범위를 확대하려면 해당 범위의 조건과 사람 승인을 별도로 확인합니다. 현재 예약 연결은 Supabase 관리 연결이므로 필요한 읽기/submit만 가능한 자격 증명으로 범위를 좁히는 구성도 반복 운영 전에 검증해야 합니다.
5. GitHub의 **저장소 → Settings → Secrets and variables → Actions**에서 필요한 서버 비밀과 검증된 운영 변수만 설정합니다. worker secret은 브라우저 공개 변수에 넣지 않습니다. 팀원에게 관리키를 공유하지 않습니다.
