## 구현 구조
1. 실행 ID와 역할(collection/drafting/weekly), KST 대상기간, 시작/완료/실패를 DB 기준으로 연결한다.
2. 기사 canonical URL과 원문 hash/revision을 중복 판정 기준으로 유지한다. 소스별 작업 임대와 stale-worker commit 방지를 유지한다.
3. 수집 엔진 후보 Crawlee는 HTTP/브라우저 요청에만 우선 적용한다. 기존 정상 출처 파서를 재사용하고 Supabase와 독립된 두 번째 영속 작업 기준을 만들지 않는다.
4. 페이지 발견/접근/본문 추출/날짜확인/관련성판정/보존/작성등록/임대/작성검사/제출/작업본확인을 구분한다.
5. 수집은 모델 호출 없이 가능한 요청·본문정리·해시·날짜근거 추출을 코드로 처리한다. 의미 판정과 한국어 작성은 기존 Codex 소비자가 담당하며 별도 유료 생성 API를 추가하지 않는다.
6. 전체 원문은 DB/보존 파일에 저장한다. 모델에는 한 번에 검토할 대상 판본을 제공하고 이미 완료된 동일 판본을 반복 전송하지 않는다. 문체·원문완독·첨부 검증은 비용 때문에 생략하지 않는다.
7. Python/Web 03시 수집 실행기와 05시 작성 실행기를 실제 배포 검증한 뒤에만 기존 결합형 경로의 책임을 제거한다.
8. 새 실행기가 같은 자료를 이중 처리하지 않도록 출처 단위로 전환하며 기존 Edge와 동시 소유하지 않는다.
9. weekly는 직전 월~일 발표 자료의 완료 원고에서 약8건을 선정해 기존 작업실에 draft 저장한다. 자동 공개하지 않는다.

## 필수 검증
- 정상 기사: 발견부터 draft 작업본 재조회까지.
- HTTP 실패: 해당 URL만 재시도 상태로 보존하고 다른 출처 진행.
- 임의 중단/재시작: DB 체크포인트에서 재개, 만료 임대로 commit 거절.
- 동일 URL/판본 반복 실행: report 중복 생성 없음.
- 빈 본문/보안화면/불명확 날짜: 정상 기사로 통과하지 않음.
- 정책·판본 일치: packet/seal/check와 서버 검사 유지.
- 비용 비교: 동일 기사 묶음의 실제 input/output/cache token 계측이 있을 때만 개선률 계산.
- 03시/05시 분리의 실제 예약 실행 증거를 수동 실행과 구별.
