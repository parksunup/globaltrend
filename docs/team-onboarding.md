# GlobalTrend 팀 온보딩 안내서

이 문서는 코딩 경험이 많지 않은 팀원이 GlobalTrend 프로젝트에 참여할 때 따라 하는 안내서입니다. 처음부터 모든 기능을 이해할 필요는 없습니다. 자신의 역할에 해당하는 자료를 만들고, Codex에게 작업을 시킨 뒤, 결과를 PR로 제출하면 됩니다.

## 1. 우리가 만드는 것

GlobalTrend는 해외 개인정보 보호 동향과 개인정보 보호 법제를 한 곳에서 조사할 수 있게 하는 웹사이트입니다.

사이트는 크게 네 가지 일을 합니다.

1. **동향 수집**: EDPB, OECD, CJEU 같은 공식 출처에서 개인정보 보호 관련 자료를 모읍니다.
2. **주간 자료 작성**: 모인 자료를 한국어로 요약하고, 주간 동향 자료 형식으로 정리합니다.
3. **법제 비교**: 한국 PIPA, 일본 APPI, 중국 PIPL, EU GDPR, UK GDPR, 미국 CCPA, 싱가포르 PDPA를 한국어로 읽고 비교합니다.
4. **근거 연결**: 동향 자료에서 언급된 법 조항을 법제 DB와 연결해 원문과 번역을 함께 보여줍니다.

자료는 자동으로 공개되지 않습니다. 수집·편집·번역 결과를 팀원이 확인하고 승인한 뒤에만 일반 사용자에게 공개합니다.

## 2. 세 사람의 역할

### 프로젝트 리드 — 사용자님

프로젝트 전체 방향과 최종 통합을 담당합니다.

- 무엇을 먼저 만들지 결정합니다.
- GitHub Issue를 만들고 담당자를 정합니다.
- Supabase, Vercel, GitHub 권한을 관리합니다.
- 팀원이 올린 PR과 Vercel Preview를 확인합니다.
- 법제·번역·동향 자료의 최종 공개 여부를 승인합니다.
- 각 팀원의 결과물을 웹사이트와 Supabase에 연결합니다.

팀원이 Supabase 운영 설정, RLS, 환경변수, `main` 브랜치를 직접 수정하지 않도록 합니다.

### 팀원 A — 법제 담당

법률 원문, 한국어 번역, 비교 기준을 준비합니다. 처음에는 웹 화면을 만들지 않아도 됩니다.

- 7개 법제의 공식 원문 URL과 현행 판본을 확인합니다.
- 한국어 번역의 출처와 번역 상태를 기록합니다.
- 17개 비교 기준에 해당하는 조항 후보를 찾습니다.
- 조항 번호·원문·번역·요약·공식 링크를 정리합니다.
- 확인하지 못한 내용은 추정하지 않고 `검토 필요`로 표시합니다.
- 결과를 `data/legal/` 아래의 CSV·JSON·Markdown 파일로 제출합니다.

### 팀원 B — 동향 담당

공식 출처의 자료를 조사하고, 수집기와 주간 자료에 사용할 기준을 준비합니다.

- EDPB·OECD·CJEU의 공식 페이지와 자료 유형을 확인합니다.
- 제목·게시일·기관·국가·주제·원문 URL을 정리합니다.
- 중복 자료와 단순 공지를 구분합니다.
- 수집 실패나 본문 누락 사례를 기록합니다.
- 주간 동향 자료에 사용할 샘플과 편집 기준을 작성합니다.
- 결과를 `data/trends/` 아래의 JSON·Markdown 파일로 제출합니다.

두 팀원은 서로의 브랜치와 폴더를 수정하지 않습니다. 서로 기다리지 않고 독립적으로 작업할 수 있도록 하는 것이 원칙입니다.

## 3. Codex 시작하기

### 3.1 Codex에서 프로젝트 열기

1. Codex 데스크톱 앱을 엽니다.
2. 프로젝트 또는 저장소를 추가하는 메뉴를 엽니다.
3. GitHub 저장소 `parksunup/globaltrend`를 선택합니다.
4. 저장소를 로컬에 받을 위치를 정합니다.
5. 작업을 시작할 때는 `main`에서 바로 작업하지 말고 새 브랜치를 만듭니다.

브랜치 이름은 작업 내용을 알아볼 수 있게 작성합니다.

```text
feat/legal-corpus-foundation
feat/legal-criteria-mapping
feat/trend-source-contracts
feat/trend-sample-fixtures
```

Codex 화면에 저장소가 보이지 않으면 GitHub 로그인 상태와 저장소 접근 권한을 먼저 확인합니다. 저장소를 새로 만들거나 복사하지 말고, 이 프로젝트의 저장소를 그대로 사용합니다.

### 3.2 먼저 읽게 할 문서

새 작업을 시작할 때 Codex에게 다음 내용을 먼저 입력합니다.

```text
이 저장소의 architecture.md, README.md, docs/team-onboarding.md를 먼저 읽고,
프로젝트 목적·공개 범위·현재 구현 상태·내 역할을 요약해 주세요.
아직 코드를 수정하지 말고, 제가 맡은 작업과 완료 조건을 이해했는지 먼저 설명해 주세요.
```

Codex가 문서를 읽은 뒤에는 요약이 맞는지 확인합니다. 문서를 읽지 않은 상태에서 바로 코드를 만들게 하지 않습니다.

### 3.3 작업을 시킬 때의 기본 규칙

모든 Codex 요청에는 다음 내용을 포함합니다.

- 내가 만들고 싶은 결과
- 수정해도 되는 폴더와 파일
- 수정하면 안 되는 부분
- 사용해야 하는 원문 또는 참고자료
- 결과 파일 형식
- 완료 조건
- 실행할 검증 명령

다음 문장을 기본으로 붙이면 좋습니다.

```text
이번 작업에서는 앱 화면, Supabase migration, 환경변수, 인증 코드를 수정하지 마세요.
결과물은 지정한 data 폴더의 파일로만 작성하세요.
확인하지 못한 내용은 추정하지 말고 검토 필요로 표시하세요.
작업이 끝나면 변경 파일, 확인한 URL, 남은 불확실성, 검증 결과를 정리해 주세요.
```

## 4. 법제 담당자가 사용할 초반 프롬프트

```text
공식 법령명, 관할권, 공식 원문 URL, 현행 판본 또는 기준일, 확인 메모를 조사하세요.

결과는 data/legal/instruments.csv로 작성하세요.
공식 출처로 확인하지 못한 값은 추정하지 말고 검토 필요로 표시하세요.
```

### 프롬프트 2: 비교 기준 조항 후보

```text
기존 seed 데이터의 17개 비교 기준을 읽고, 각 기준에 대해 한국 PIPA와 일본 APPI의
관련 조항 후보를 정리하세요.
```

### 프롬프트 3: 번역 검토

```text
원문, 공식 원문 URL, 조항 번호, 번역문, 번역상 어려운 용어, 사람 검토가 필요한 부분을
각각 분리해 주세요.

번역은 초안으로 표시하고, 원문에 없는 해석은 추가하지 마세요.
```

## 5. 동향 담당자가 사용할 초반 프롬프트

### 프롬프트 1: 출처별 수집 규칙

```text
동향 담당으로 작업합니다. EDPB, OECD, CJEU/CURIA의 공식 페이지를 조사하세요.
각 출처에 대해 시작 URL, 자료 유형, 제목 위치, 게시일 위치, 본문 위치,

결과는 data/trends/source-configs/edpb.json,
```

```text

자료마다 원문 링크, 게시일, 기관, 국가, 핵심 내용, 개인정보 보호상 의미,

확인되지 않은 법적 결론은 쓰지 말고, 사실과 해석을 별도 항목으로 나누세요.
결과는 data/trends/weekly-template.md로 작성하세요.
```

## 6. GitHub에서 작업을 제출하는 방법

작업을 시작할 때는 본인 브랜치에서 작업합니다. `main`에 직접 push하지 않습니다.

1. Codex에서 작업 브랜치를 만듭니다.
2. Codex에게 필요한 파일을 작성하게 합니다.
3. 변경 파일과 원문 URL을 확인합니다.
4. Codex에게 TypeScript 검사 또는 해당 작업의 검증 명령을 실행하게 합니다.
5. Codex에게 PR을 만들어 달라고 요청합니다.
6. PR 설명에 변경 내용, 확인한 근거, 남은 검토 필요 항목을 적습니다.
7. 사용자님이 PR과 Preview를 확인한 뒤 merge합니다.

PR을 만들 때 사용할 프롬프트는 다음과 같습니다.

```text
작업 결과를 검토 가능한 PR로 만들어 주세요.
PR 제목은 변경 목적이 드러나게 작성하고,
본문에는 변경 파일, 확인한 공식 URL, 검토 필요 항목, 실행한 검증을 적으세요.
main 브랜치에는 직접 merge하지 마세요.
```

## 7. 사용자님이 PR에서 확인할 것

코드를 모두 이해하지 못해도 다음 항목은 확인할 수 있습니다.

- 요청한 파일과 결과물이 실제로 포함되어 있는가
- 공식 URL이 들어 있는가
- 확인하지 못한 부분이 숨겨지지 않고 표시되어 있는가
- 팀원의 작업 범위를 넘어 앱·권한·환경변수를 수정하지 않았는가
- Preview 또는 검증 결과가 있는가
- 기존 자료를 삭제하거나 덮어쓰지 않았는가

법제·번역 자료는 코드가 정상적으로 실행되는 것만으로 완료로 보지 않습니다. 공식 원문과 사람이 확인할 수 있는 근거가 있어야 합니다.

## 8. 작업을 시작하는 순서

1. PR #7이 merge되었는지 확인합니다.
2. 이 문서와 `architecture.md`, `README.md`를 읽습니다.
3. 법제 담당자는 `feat/legal-corpus-foundation` 브랜치를 만듭니다.
4. 동향 담당자는 `feat/trend-source-contracts` 브랜치를 만듭니다.
5. 각자 첫 번째 프롬프트를 Codex에 입력합니다.
6. 결과 파일과 PR을 제출합니다.
7. 사용자님은 Preview와 근거 자료를 확인합니다.

두 팀원은 서로의 작업이 끝나기를 기다릴 필요가 없습니다. 사용자님이 결과물을 검토한 뒤 나중에 Supabase와 웹 화면에 통합합니다.
