# 해외 개인정보 동향 원고 작성 지침

기준 ID: `privacy-report-ko-48-reference-v2`
적용 대상: 수집 출처와 공개 여부에 관계없이 GlobalTrend에 등록하는 모든 해외 동향의 제목·핵심 요약·상세 본문. 주간호에 선정하지 않은 원고와 기존 원고의 수정에도 동일하게 적용한다.

## 1. 이 지침의 근거와 목표

사용자가 제공한 최근 1년의 주간동향 PDF **48개 모두의 해외 기사 본문**을 읽고 작성한 지침이다. 검토 범위는 각 PDF의 물리 페이지 4~8, 총 240쪽이며, 국내 기사는 제외했다. 표지·목차나 추출 통계만 확인한 것을 본문 검토로 대신하지 않는다. 대상 파일과 호별 관찰은 [48개 자료 검토 기록](trend-reference-reading-notes.md)에 남긴다.

목표는 원문을 짧게 요약하는 것이 아니라, 해당 사건·제도·보고서를 처음 접하는 한국어 독자가 **무슨 일이 있었고, 무엇이 달라졌으며, 왜 그런 판단이나 조치가 나왔는지** 이해할 수 있는 동향 원고를 만드는 것이다. 참고자료의 정보량과 설명 수준, 공무원 보고서에 쓰는 간결한 개조식 문체를 따른다.

PDF의 글꼴·지면·색상·로고·기호 체계를 복제하라는 뜻이 아니다. 모든 기사에 소제목을 붙이거나 `○ → - → · → ※`의 계층을 강제하지 않는다. 원고의 내용과 문체를 학습하고, 화면의 표현은 서비스 디자인에 맡긴다.

참고자료는 **문체와 편집 수준을 판단하는 자료**다. 그 안의 과거 사실·번역·법적 설명을 새 기사의 근거로 전용하지 않는다. 사실은 해당 기사의 공식 원문과 연결된 법령·판결·보고서에서 확인한다. 참고자료에 등장하는 표현도 사용자 지정 용어와 다르면 [용어집](translation/glossary.md)을 우선한다.

## 2. 먼저 이해해야 할 참고자료의 특징

### 2.1 제목이 아니라 사건의 실체를 설명한다

`지침을 발표하고 개인정보 보호를 강조`라고만 쓰지 않는다. 누가 어떤 상황에서, 어떤 주체에게, 어떤 처리 행위를 어떻게 바꾸도록 했는지 설명한다. 참고자료의 협업도구 기사는 도구 이용을 알리는 데 그치지 않고 학생·교직원 정보, 공익적 임무라는 처리 근거, 동의의 한계, 프로세서 계약, 국외 이전을 연결한다(2026년 제34호, 물리 6쪽).

### 2.2 보통 기사에도 여러 개의 구체적인 사실이 있다

대표기사는 한 쪽을 사용해 배경과 세부 조치를 길게 전개하며, 일반 기사는 대체로 반 쪽 안팎에서 여러 사실을 연결한다. 일반 기사에서도 조사 대상·기간·조건·예외·수치·구체적 조치·후속 절차 중 필요한 내용이 빠지지 않는다. `개최 → 두 주제 논의 → 다시보기 공개` 같은 세 줄짜리 공지를 완성 원고로 간주하지 않는다.

예를 들어 제38호의 구글 위치정보 제재 기사는 조사 착수 배경, 조사 기간, 세 가지 기능, 기능별 위반 내용, 이용자의 통제권 문제, 과징금, 시정 기한을 설명한다. 제41호의 Xandr 기사는 RTB 정보 흐름, 민감한 정보의 성격, 공동 컨트롤러의 책임, 동의 확인, 위반 기간과 과징금 산정까지 이어간다.

### 2.3 논리 관계를 보존한다

짧은 문장의 나열만으로 개조식 문체가 완성되지 않는다. 배경을 알아야 판단을 이해할 수 있으면 배경을 먼저 둔다. 조건을 알아야 적용 범위를 이해할 수 있으면 조치와 조건을 같은 항목에 둔다. `다만`, `이에 따라`, `또한`은 실제 관계가 있을 때 쓴다. 원문에서 함께 다룬 사실이라고 모두 인과관계로 연결하지 않는다.

### 2.4 기관의 주장과 확정 사실을 구분한다

기관이 지적한 위험은 `기관은 … 위험을 지적`으로, 법원이 판단한 내용은 `법원은 … 판단`으로 쓴다. 법안 발의자의 정책 목적을 이미 검증된 효과로 바꾸지 않는다. 제안된 개정, 확정된 규칙, 시행 예정인 의무, 기관이 기대하는 실무 기한을 각각 구별한다.

### 2.5 구체적인 설명이 문체를 만든다

`공식 발표`, `강력한 조치`, `체계적인 관리`, `보호 강화 필요성`을 반복하는 대신 실제 변경 내용과 행위를 쓴다. 정보가 빈약한 원고를 종결어미만 바꿔 제출하지 않는다. 원문을 충분히 읽어야 문장이 자연스럽고 밀도 있게 구성된다.

## 3. 작성 전에 확보할 자료

1. 공식 보도자료나 공지 본문을 처음부터 끝까지 읽는다. 검색 결과 요약, 제목, 첫 문단만으로 작성하지 않는다.
2. 본문이 연결하는 판결·결정문·법률안·규칙·지침·보고서·첨부 PDF를 확인한다. 짧은 공지는 연결 문서가 실질적인 원문인 경우가 많다.
3. 사건의 원인이 앞선 처분이나 조사라면 이전 공식 자료를 함께 읽는다. 이번 공지가 새로 알린 내용과 과거 배경을 구분한다.
4. 공식 원제, 발행 기관, 게시일, 사건일, 문서 판본, URL, 실제로 읽은 범위를 내부 기록에 남긴다.
5. 기관이 다른 기관의 처분을 재소개한 경우 원 처분 기관 자료도 확인한다. EDPB의 회원국 제재 소개와 해당 국가 감독기관 원문은 서로 보완할 수 있다.
6. 제목·메뉴·목차만 내려받았거나 JavaScript 안내 화면만 받은 경우에는 본문을 확보했다고 기록하지 않는다. 접근 오류·본문 누락·미확인 첨부는 명확히 구분한다.

### 짧은 원문을 보완하는 순서

`짧으니 짧게 작성`하기 전에 다음을 수행한다.

- 법 개정 공지: 개정 개요 → 개정 조문 → 신구조문 비교표 → 시행·경과조치 확인.
- 제재 종결 공지: 원 제재 결정 → 위반 행위 → 시정명령 → 제출된 개선조치 → 종결 범위 확인.
- 보고서 발간 공지: 보고서 요약 → 분석 결과·표 → 권고·한계·결론 확인.
- 행사 다시보기 공지: 프로그램·발표자료 → 실제 공개된 발언·영상에서 확인 가능한 논의 확인. 프로그램만 읽었으면 논의 의제까지만 설명하고 참석자의 결론을 만들어내지 않는다.
- 도구 출시 공지: 사용 설명·질문 항목·출력 예시·적용 법률 확인. 도구가 대신하지 못하는 판단도 원문에 있으면 설명.
- 국제회의 공지: 공동성명·채택 문서 → 실무협력 항목 → 이행 주체·일정 확인.

이 과정을 거쳐도 근거가 짧으면 확인된 사실만 쓴다. 글자 수를 맞추려고 일반론을 삽입하거나 없는 논의를 창작하지 않는다. 보완 자료 접근 실패는 내부 검토 기록에 남긴다.

## 4. 분량과 정보 밀도

분량은 항목 수나 어미가 아니라 **독자가 사건을 이해하는 데 필요한 정보가 담겼는지**로 판단한다. 다음 수치는 편집 시 경보 기준이며, 모든 기사에 강제하는 상·하한이 아니다. 공백 포함 한국어 상세 본문 기준으로 판단한다.

| 종류 | 검토를 시작할 때의 분량 감각 | 반드시 확인할 내용 |
| --- | --- | --- |
| 보통 제재·판결·지침 기사 | 대체로 700~1,200자 안팎부터 정보 누락을 점검 | 사안·구체 행위·핵심 판단·조건·결과 |
| 복수 쟁점·보고서·중요 제도 개편 | 1,200자를 넘겨도 필요한 사실을 유지 | 세부 내용과 차이·수치·한계·일정 |
| 대표기사에 해당하는 복합 정책 | 1,800~2,500자 이상도 가능 | 배경·조치별 내용·담당기관·예외·이행 |
| 근거를 끝까지 확인해도 짧은 공지 | 분량을 억지로 늘리지 않음 | 새 사실·범위·관련 자료와 확인 한계 |

위 범위는 48개 자료를 읽고 도출한 **작성용 권장 감각**이지, 기사별 글자 수를 자동 분리해 산출한 통계값이 아니다. 참고자료를 근거 없이 `평균 정확히 ○○자`라고 설명하지 않는다. 원문이 충분한데도 본문이 200~400자에 그치면, 의도적 압축인지 핵심 사실 누락인지 반드시 다시 점검한다. 사용자가 직접 제시한 짧고 완결된 원고는 문맥과 충족 내용을 보고 판단한다.

일반 기사에는 보통 5~8개 이상의 독립된 사실이 들어갈 수 있다. 이것은 항목을 5~8개 만들라는 뜻이 아니다. 한 항목에 서로 이어지는 2~3개 사실을 담을 수 있다. 반대로 한 사실을 세 항목으로 쪼개 분량을 부풀리지 않는다. 3개 항목 고정, 문장 2개 고정, 요약 250자 고정 같은 제한을 두지 않는다.

### 분량이 부족할 때 되물어야 할 것

- 어떤 시스템·서비스·행위가 문제였는가?
- 어떤 정보와 누구의 정보가 처리됐는가?
- 문제가 드러난 조사·민원·사고의 경위는 무엇인가?
- 판단·권고의 근거와 핵심 이유는 무엇인가?
- 의무를 지는 주체, 적용 조건, 예외는 무엇인가?
- 실제 개선조치나 권리 행사 방법은 무엇인가?
- 기한·시행일·후속 심리·입법 절차는 무엇인가?
- 보고서라면 분석 기간·대상·방법·수치·권고는 무엇인가?

이 질문에 답하는 사실을 원문에서 추가한다. 본문 끝에 `시사하는 사례`, `책임 있는 활용이 중요`, `지속적인 관심 필요`를 덧붙여 채우지 않는다.

## 5. 제목·핵심 요약·상세 본문의 역할

### 제목 (`title_ko`)

`국가·기관, 대상과 구체적 조치`를 기본으로 한다. 독자가 목록에서 사건의 새로움을 알 수 있어야 한다.

- 약함: `프랑스 CNIL, 개인정보 보호 강조`
- 개선: `프랑스 CNIL, 병원의 접근통제·침해 통지 위반에 50만 유로 과징금 부과`
- 약함: `DPC, AI 관련 보고서 발표`
- 개선: `아일랜드 DPC, 2021~2025년 AI 감독 활동과 사전 협의 결과 공개`
- 단계 오류: 소장 제출을 `위법 확정`으로, 법안 발의를 `새 규정 시행`으로 제목에 쓰지 않는다.

### 핵심 요약 (`summary_ko`)

주체·새 조치·대상·핵심 특징을 한 문단으로 전달한다. 상세 본문을 통째로 복사하지 않는다. 제목과 같은 말을 조금 늘리는 데 그치지도 않는다. 본문에서 설명할 실질을 하나 이상 담는다.

예: `아일랜드 DPC, AI 제품·서비스에 대한 사전 협의와 집행 활동을 분석하고 투명성·적법한 처리 근거·보호조치 관련 주요 권고와 출시 전 협의 방향을 제시`

### 상세 본문 (`details_ko`)

소제목 없는 `- 문단`을 빈 줄로 구분하는 기존 원고 계약을 사용한다. 이는 참고 PDF의 지면 기호를 새로 강제하는 것이 아니라, 서비스가 읽어 표시하는 기존 입력 방식이다. 모든 항목에 `배경`, `핵심 내용`, `시사점` 같은 소제목을 달지 않는다.

일반적인 흐름은 `사건·제도 배경 → 핵심 사실·판단 → 세부 내용·조건 → 결과·후속 절차`다. 기사의 성격에 맞춰 순서를 바꿀 수 있다. 원문에 없는 배경이나 시사점을 의무적으로 만들지 않는다. 조문별 행정명령처럼 원문 자체가 조문 구획으로 설명되어야 이해되는 경우에만 해당 구분을 유지한다.

## 6. 공무원 보고서체: 어미가 아니라 문장 전체를 다듬는다

### 6.1 기본 종결

`발표`, `공개`, `규정`, `명시`, `확인`, `판단`, `설명`, `지적`, `권고`, `요구`, `명령`, `추진`, `예정`, `해당`, `포함` 등 문장 내용에 맞는 간결한 서술을 사용한다. 필요한 곳에는 `…한 것으로 봄`, `…이었음`, `…에 해당함`처럼 자연스러운 명사형을 쓴다.

`~합니다`를 `~하다`로 바꾸는 것은 이 문체가 아니다. `있었다`, `단정하지 않다`, `중요하다`, `필요하다`로 말끝만 반말로 바꾸지 않는다. `함`을 일괄 추가하는 것도 피한다.

| 고쳐야 할 문장 | 더 적절한 문장 | 이유 |
| --- | --- | --- |
| `환자 진료정보가 포함돼 있었다` | `해당 시스템에는 환자의 진료정보도 포함` | 구어적 과거형 대신 확인 사실을 간결하게 제시 |
| `CNIL은 유효한 동의가 필요하다고 말했습니다` | `CNIL은 중개업체를 통해 확보한 동의도 마케팅 사업자가 유효성을 확인할 책임이 있다고 명시` | 어미뿐 아니라 책임의 주체·내용을 구체화 |
| `모든 정보가 반출됐다고 단정하지 않다` | 사실 확인 후 `공격자는 시스템을 탐색한 뒤 대량의 정보를 추출한 것으로 확인` | 편집자의 유의 문구를 쓰지 않고 확인된 사실을 작성 |
| `보안을 강화해야 한다고 했다` | `감독기관은 원격접속 다중요소 인증과 접근권한 제한, 이상행위 탐지를 요구` | 추상적 조언을 실제 조치로 대체 |
| `해당 결정은 최종 판단은 아닙니다` | `이번 판결은 취소소송의 적법성에 관한 판단이며, 개인정보 처리의 위법성은 후속 본안 심리에서 다뤄질 예정` | 무엇이 판단됐고 무엇이 남았는지 설명 |

### 6.2 한 항목 안의 문장 호흡

한 문장에 별개 사건을 모두 넣지 않는다. 관련된 내용을 두 문장으로 나눌 수 있으나 문체는 일관되게 유지한다. 첫 문장은 사건이나 조치, 다음 문장은 필요한 배경·조건·의미를 설명한다. `…판단. 이에 따라 …환송`처럼 자연스러운 연결을 사용한다.

행위자·행위·대상을 확인한다. `개인정보 이용 확인 및 조치 추진 강화`처럼 명사를 쌓아 무엇을 했는지 알기 어렵게 만들지 않는다. `이를 통해`, `이에 대해`, `이러한`의 지시 대상이 모호하면 명사를 다시 쓴다.

### 6.3 불필요한 관공서풍 수사도 줄인다

`선제적이고 체계적인 통합 거버넌스 구축을 통한 실효성 제고 도모` 대신 실제 조치를 쓴다. `전격`, `파격적`, `막대한`, `강력한`, `획기적`, `대폭`은 원문에서 주장한 정도가 중요할 때 주체를 밝혀 제한적으로 쓴다. 원문의 홍보성 문구를 객관적 사실처럼 옮기지 않는다.

### 6.4 한국어로 이해되게 쓴다

전문용어를 모두 일상어로 치환할 필요는 없다. 컨트롤러·프로세서처럼 법률상 역할은 유지하되, 사건에서 누가 어떤 목적·수단을 결정했는지 설명한다. `당해 데이터 처리에 대한 투명성 요건 준수 관련 사안`보다 `이용자에게 위치정보의 수집·이용 사실을 충분히 알렸는지가 쟁점`처럼 구체적으로 쓴다.

## 7. 기사 유형별 내용 선택

### 7.1 과징금·시정명령·제재 종결

대상 기업과 서비스, 민원·조사 경위, 실제 처리 행위, 정보·영향 범위, 위반 의무와 이유, 처분 내용, 금액·산정 요소, 시정 기한, 불복·종결 범위를 확인한다. 모든 사건에 모든 항목이 존재하지는 않지만, 있는 핵심 내용을 버리지 않는다.

종결은 과거 위반이 없었다는 뜻이 아니다. 시정명령 이행을 인정한 것인지, 과징금을 취소한 것인지, 예정된 이행강제금을 부과하지 않은 것인지 각각 구분한다. 제3자의 기술·동의 수집에 의존해도 책임이 남는다는 판단은 해당 책임 주체와 함께 설명한다.

### 7.2 법원 판결·법무관 의견·소송

당사자와 분쟁의 배경 → 법적 질문 → 판단 기준·이유 → 주문·절차상 효과 → 남은 심리 순으로 읽는다. 법무관 의견은 법원 판결로 쓰지 않는다. 취소소송 적법성 판단은 본안 위법성 판단과 구별한다. `청구 기각`, `각하`, `원심 취소`, `환송`, `집행정지`를 혼용하지 않는다.

### 7.3 법안·개정·규칙

왜 바꾸는지, 적용 대상과 범위, 기존 규정과 달라지는 내용, 의무·권리·예외, 제재·집행 주체, 입법 단계, 시행·유예·경과조치를 확인한다. `공포 후 2년 이내 정령으로 정하는 날`을 `2년 후 시행 확정`으로 바꾸지 않는다. 여러 주체에 서로 다른 시행일이 적용되면 따로 쓴다.

### 7.4 지침·권고·실천강령

누가 활용하는 문서인지, 어떤 처리 활동에 적용되는지, 새로 명확해진 기준, 실제 이행 방법, 예외·한계, 초안/최종 여부, 의견수렴 기한을 설명한다. 문서의 목차만 옮기지 않는다. `적법성·투명성·보안 설명`보다 각 원칙이 어떤 행동을 요구하는지 쓴다. 자발적 강령이 법적 의무 입증 수단이라면 의무와 수단을 분리한다.

### 7.5 보고서·연례보고·실태조사

대상 기간과 모집단·표본, 조사 방법, 핵심 수치와 비교 기준, 원인·양상, 구체 사례, 권고와 후속 계획을 확인한다. 모든 통계를 붙이지 말고 기사 결론을 뒷받침하는 통계를 고른다. 응답자 비율을 전체 국민 비율로 바꾸거나 상관관계를 인과관계로 쓰지 않는다.

### 7.6 기술·AI·PET

기술이 어떻게 작동하는지 필요한 만큼 설명하고, 어떤 데이터가 누구에게 노출되는지, 줄어드는 위험과 남는 위험, 적용 사례, 도입 조건·운영상 한계·법적 의무를 연결한다. 암호화·가명처리·익명처리를 동의어로 쓰지 않는다. PET를 쓰면 개인정보보호법 적용이 사라진다고 설명하지 않는다.

### 7.7 행사·연설·교육·도구

행사 명칭·개최·다시보기 유무만으로 끝내지 않는다. 실제 논의된 질문이나 발표된 입장, 문제의 배경, 참여 주체의 역할, 공개된 결과물·실무 자료, 활용 방법을 확인한다. 프로그램에 있는 질문을 이미 합의한 결론으로 쓰지 않는다. 연설에서 예고한 계획과 시행된 정책을 구분한다.

### 7.8 국제·지역 협의체와 표준기구

G7·GPA·APPA·APEC·OECD·RIPD·베를린 그룹 및 ISO·ETSI·NIST·TC260 등의 문서도 실질적인 주간 동향 대상이다. 채택·서명·발효·시범사업을 구별하고, 원칙의 구체적 내용, 이행 주체, 기술 지표와 활용 사례, 후속 일정을 설명한다. 주간 수집 대상 여부와 작성 지침은 다른 문제이며, 이 지침을 이유로 월간 수집으로 줄이지 않는다.

## 8. 사용자 확인을 거친 번역 원칙

전체 목록과 법률별 예외는 용어집을 확인한다. 아래는 원고를 고칠 때 특히 자주 틀리는 기준이다.

- foundation model: **파운데이션 모델**. agentic AI: **에이전트 AI**.
- 컨트롤러·프로세서 개념 유지. 싱가포르 data intermediary: **데이터 중개자**. 중국 PIPL의 개인정보처리자는 중국법 정의에 따라 별도 설명.
- PET·TEE는 한국어 명칭 뒤 영어 약자를 괄호로 병기. secure multiparty computation: **안전한 다자간 연산(MPC)**.
- neurodata: **신경 데이터**. profiling: **프로파일링**이며 원어를 억지로 병기하지 않음.
- special categories of personal data: **특별한 유형의 개인정보**, 첫 등장에 원어와 설명 병기. 해당 법의 범위를 한국법의 민감정보와 자동 동일시하지 않음.
- 가명처리/가명정보, 익명처리/익명정보를 사용하되 법률별 정의·고유 명칭 구분. CCPA는 비식별화/비식별정보. 일본은 가명가공정보·익명가공정보·개인관련정보 유지.
- 일본 要配慮個人情報는 **요배려 개인정보(배려가 필요한 정보)**로 독자의 이해를 돕고 법률상 별도 범주임을 설명. 보유 개인데이터/보유 개인정보 구분.
- automated decision-making: **자동화된 의사결정**. restriction of processing: **처리 제한**, 권리는 **처리 제한권**.
- accountability: **책임성**. legitimate interests: **정당한 이익**. adequacy decision: **적정성 결정**. binding decision: **구속력 있는 결정**.
- data protection by design and by default: **설계 및 기본 설정에 의한 개인정보 보호**. privacy by design만 있는 경우 기본 설정까지 임의로 추가하지 않음.
- lead supervisory authority: **선임 감독기관(lead supervisory authority)**, reprimand: **견책(reprimand)**, information notice: **정보제출 요구 통지(information notice)**. 원어는 각 독립 원고 첫 등장에 병기.
- remedy/redress는 구제·구제수단을 기본으로 하고 금전적 배상은 문맥에 맞게 손해배상 등으로 구분.
- CCPA 판매·공유는 원어 없이 각각의 정의를 설명. contractor는 **계약자(contractor)**로 첫 등장에 병기.
- deemed consent는 명칭 **동의 간주**, 문장에서는 **동의한 것으로 본다**. 개인정보 이동권은 공통 설명에서 **개인정보 이동권(전송요구권)**을 사용하되 국가별 권리를 동일한 제도로 단정하지 않음.
- call for evidence는 모집 대상을 보고 자료·사례 수집 또는 의견·자료 모집, consultation은 실제 절차에 맞게 의견수렴 등으로 번역.
- compatibility of purposes는 **목적 간 양립가능성**. 문서 폐기 맥락의 confidential waste는 **폐기 대상 기밀문서**. 다른 매체는 실제 대상을 확인.

### disclose / disclosure

특정 기관·사업자 등 수신자에게 전달하거나 접근 가능하게 하면 `제공`, 불특정 다수가 볼 수 있게 하면 `공개`, 정보주체에게 처리 내용을 설명하면 `고지·알림·정보 제공`으로 문맥에 맞게 옮긴다. 외국법의 disclosure를 한국법상 제3자 제공과 자동 동일시하지 않는다. 하나의 조항이 여러 행위를 포괄하면 그 범위를 풀어 설명한다.

### breach / infringement / violation

단어 하나에 고정 번역을 걸지 않는다. 실제 사건에서 외부 반출·노출이 확인됐으면 유출, 무단 열람이면 무단 열람, 분실·파기·변경·접근 불능이면 확인된 사건 유형을 구체적으로 쓴다. 동의 없는 위법 수집·이용은 그 행위를 설명한다. GDPR의 personal data breach는 기밀성뿐 아니라 무결성·가용성 문제도 포괄하므로 모두 유출로 줄이지 않는다. 법률을 설명할 때는 각국 정의와 통지 요건을 구체적으로 풀어 쓴다.

`외부 반출이 확인되지 않음`과 `공지가 반출 여부를 다루지 않음`은 다르다. 확인하지 못한 것을 부정 사실로 쓰지 않는다. 반대로 공식 원문이 대량 추출과 정보 탈취를 명시하면 이를 무단 접근만으로 축소하지 않는다.

## 9. 풍부한 사례: 무엇을 어떻게 고치는가

아래 사례는 참고자료에서 배운 설명 방식을 실제 편집에 적용하기 위한 예시다. 번호별 항목 수를 모든 기사에 강제하지 않는다. 원문의 날짜·처분·수치는 실제 제출 때 해당 공식 판본과 다시 대조한다. 잘못된 문장은 이전의 부실한 작성 방식을 드러내기 위한 것이며 재사용하지 않는다.

### 사례 1. 사용자 제시 기준: WhatsApp 소송

사용자가 직접 제시한 다음 원고는 문체·응집성과 절차 구분의 기준이다.

> - EU 사법재판소는 2026년 2월 10일 WhatsApp Ireland가 유럽데이터보호이사회(EDPB)의 구속력 있는 결정을 직접 다툴 수 있다고 판단. EDPB 결정은 국경을 넘는 분쟁에서 감독기관들의 입장을 조정하고, 아일랜드 감독기관에 시정조치와 과징금 조정을 요구한 결정이었음
>
> - 사법재판소는 해당 결정이 WhatsApp Ireland에 직접 관련된 행위이므로 EU 법원에서 취소소송의 대상이 될 수 있다고 봄. 이에 따라 소송을 심리하지 않고 각하한 일반재판소의 결정을 취소하고 사건을 환송
>
> - 이번 판결은 소송의 적법성과 법원 심리 가능성에 관한 판단임. WhatsApp의 개인정보 처리 자체가 GDPR을 위반했는지, EDPB의 시정조치와 과징금이 적절한지는 일반재판소의 후속 본안 심리에서 다뤄질 예정

왜 적절한가: 결정을 다툰 배경, 직접 관련성 판단, 원심 취소·환송, 본안 미판단이 이어진다. 마지막 항목은 작성자에게 `일반화하지 말 것`이라고 지시하는 대신 독자가 알아야 할 판단의 범위를 설명한다. 이 사례가 3항목이라고 모든 기사를 3항목으로 줄이지 않는다.

### 사례 2. Solocal 시정명령 종결

부실한 방식: `CNIL은 과징금을 부과했습니다. 회사가 자동 점검을 도입했습니다. 조치를 종결했습니다.`

개선 전개:

- 프랑스 CNIL은 마케팅 사업자 Solocal Marketing Services가 동의 수집 양식의 적법성을 확인하는 체계를 마련함에 따라 앞서 부과한 시정명령 절차를 종결
- Solocal은 데이터 중개업체 등을 통해 확보한 잠재고객 정보를 이용해 광고주를 대신하여 문자·이메일 홍보를 수행. CNIL은 최초 수집 단계의 양식이 자유롭고 명확한 동의를 보장하지 못한 문제 등을 이유로 2025년 90만 유로 과징금과 시정명령을 부과한 바 있음
- 회사는 최초 수집자가 사용한 동의 양식을 자동 분석하고 담당자가 추가로 검토하는 체계를 도입. CNIL은 해당 조치가 엄격하게 적용될 경우 유효하지 않은 동의에 기반한 홍보를 막는 데 도움이 된다고 평가
- CNIL은 정해진 기간 내 개선조치가 이행된 점을 인정해 하루 1만 유로의 예정된 이행강제금을 부과하지 않기로 결정. 이는 원래 과징금을 취소하거나 개별 동의의 적법성을 모두 보증한 결정과 구별
- 중개업체가 동의를 확보했더라도 마케팅 사업자가 유효성을 확인할 책임은 유지되며, 점검을 통과한 양식에 문제가 남은 경우에도 해당 사업자의 책임이 사라지지 않는다고 명시

실제 원고에서는 기한·기준일·추가 위반 근거를 공식 결정과 대조해 보완한다. 중요한 점은 자동 분석 도입이라는 기술적 사실만 적지 않고 기존 위반·개선·종결 효과·남은 책임을 설명하는 것이다.

### 사례 3. 병원 사고: 사실 축소와 편집 메모 제거

문제 문장: `정보에 대한 무단 접근이며, 모든 정보의 외부 반출 여부까지 단정하지 않다`

이 사건의 공식 CNIL 원문은 공격자가 며칠간 시스템을 탐색하고 대량의 정보를 추출한 사실을 명시한다. 따라서 원문 확인 없이 `반출 미확인`을 넣으면 보수적 표현이 아니라 사실 오류가 된다.

개선할 정보 배열:

- 공격이 발생한 시기와 환자 52만 4,867명·환자가 지정한 신뢰인 20만 2,246명의 정보가 영향을 받은 사실을 제시. 진료정보 등 정보 종류를 함께 설명
- 외부 접속의 VPN·다중요소 인증 미비, 진료팀에 한정되지 않은 접근권한, 이상행위 탐지 부족이 어떻게 단일 계정 침입을 대규모 피해로 키웠는지 연결
- 대량 정보 추출과 통지 누락을 설명하고 개인정보 보안 의무 위반과 정보주체 통지 의무 위반을 구분
- 과징금 50만 유로, 시정조치, 조치별 기한을 설명. 조사 중 개선조치를 취했다는 사실과 남아 있는 이행 의무도 구분

`시스템에는 진료정보가 포함돼 있었다`처럼 문체가 섞인 한 문장을 고치는 데 그치지 않고, 사고 원인과 처분 이유가 이해되는 글로 다시 작성한다.

### 사례 4. 행사 공지: CNIL Rencontres Informatique et Libertés

부실한 원고: `행사를 개최 / 스마트 안경과 제재 논의 / 다시보기 공개`

보완할 내용: 행사가 기술 변화와 개인정보 보호법의 관계를 논의하는 자리라는 목적, 스마트글래스의 눈에 띄지 않는 촬영과 새로운 사용 방식, 기술·산업·법률·사회학 관점의 참여, 제재의 규제상 역할을 다룬 별도 논의, 전년도 집행 수치가 제시된 배경, 공개된 다시보기·자료를 확인한다.

문장 예: `스마트글래스 관련 논의에서는 일반 안경과 유사한 외형의 촬영 장치가 주변인의 사생활에 미치는 위험과 일상적 활용의 편의를 함께 검토하는 질문을 제시. 규제기관과 기술기업 및 연구자 등이 참여해 기술 특성과 규제 대응을 서로 다른 관점에서 다루도록 프로그램을 구성`

프로그램만 확인했다면 `모든 참석자가 규제 강화에 합의`라고 쓰지 않는다. 영상이나 발표문을 읽고 확인한 구체적 주장만 추가한다. 이름을 길게 나열하는 것으로 내용량을 채우지 않는다.

### 사례 5. 삭제권 제재: EXTIA

부실한 원고: `삭제 요청 대응이 미흡해 과징금 부과. 권리 보장 필요`

보완 전개: 채용 과정에서 보유한 직원·지원자 정보 → 민원과 점검의 배경 → 2024년 삭제 요청 265건 중 다수의 미처리·불충분한 처리 → 실제 삭제 누락, 조치 결과 미고지, 1개월 기한 초과를 구별 → GDPR 제12조·제17조 판단 → 앞선 지적과 반복 여부 → 과징금. 서로 다른 미흡 유형과 수치를 전체 요청 건수와 혼동하지 않는다.

### 사례 6. 마케팅 형사사건: Brown Thomas Arnotts

부실한 원고: `동의 없이 광고를 보내 제재. 수신거부 기능 점검 필요`

보완 전개: 유효한 동의와 수신거부 수단을 둘러싼 혐의 → 제3자 소프트웨어가 수신거부를 간헐적으로 막은 현상과 별도 거부 뒤에도 이어진 메시지 → 전체 혐의 중 법정에서 다룬 표본 혐의 → 유죄 인정 → 법원이 적용한 처리와 자선단체 지급·소송 비용 → 앞선 경고와 개선조치 → 외부 업체 이용에도 남는 사업자 책임. 자선단체 지급액과 과징금은 구별한다.

### 사례 7. AI 감독 활동 보고서

부실한 원고: `DPC는 AI 감독을 강화하고 사전 협의를 권고`

참고자료 제39호의 전개: 분석 기간(2021~2025년) → AI 협의 약 180건과 생성형·비생성형 구분 → 연도별 증가 → 권고를 받은 제품 비율과 권고 분야 → 지연 없이 출시된 비율 → 출시 지연·취소 사례 → 최소 8주 전 협의 → Grok 관련 긴급 절차 사례. 수치가 어떤 집단과 기간을 대상으로 하는지 확인하고, 협의 자체를 법정 허가제로 설명하지 않는다.

### 사례 8. 신경 데이터 보고서

부실한 원고: `신경 데이터가 민감하므로 보호가 필요하며 국제협력 중요`

좋은 전개: 어떤 신경 신호를 어떤 장비·서비스에서 수집하는지 → 임상·연구·소비자 환경의 차이 → 신호를 가공하고 정신 상태 등을 추론하는 과정 → 기존 법률의 적용과 중첩·공백 → 혁신 주체 조사에서 확인한 어려움 → 보고서가 제안한 대응 방향. 원문이 분석한 관할권이나 조사 표본을 확인하고 모든 신경 데이터가 모든 나라에서 법정 민감정보라고 단정하지 않는다.

### 사례 9. MPC·TEE·PET

부실한 원고: `신기술로 개인정보를 안전하게 이용할 수 있음`

참고자료 제38호의 MPC 기사에서 배울 점: 원본을 서로 공개하지 않고 공동 연산하는 방식 → 통계·자금세탁 탐지·모델 학습·추론의 실제 활용 → 최소화·기밀성 효과 → 개인정보 및 공동 컨트롤러 의무가 남는다는 점 → 공모·악의적 입력·추론·연산 부담 → 영향평가. TEE는 처리 중 보호와 하드웨어 신뢰·공급망·서비스 거부 한계를 설명한다. 서로 다른 PET의 보안 가정을 합치지 않는다.

### 사례 10. breach의 번역

외부 전송이 확인된 공격은 `유출`, 외부 반출 없이 접근이 차단된 랜섬웨어는 `접근 불능` 등 실제 상태를 쓴다. 법률상 신고 대상의 포괄 개념을 설명할 때는 `분실·파기·변경·무단 제공·접근 등 해당 법이 규정한 사고`로 필요한 범위를 구체화한다. 동의 없는 수집을 모두 `유출`로 바꾸지 않는다.

### 사례 11. disclose의 번역

- `기관이 은행에 고객정보를 disclose`: 문맥상 특정 수신자에게 전달하는 **제공**인지 확인.
- `명단을 누구나 보는 웹사이트에 disclose`: **공개**.
- `처리 목적을 이용자에게 disclose`: **고지·설명·정보 제공**.
- 복수 행위를 포괄하는 조문: 수신자·방식·법률상 범위를 풀어 설명. 일괄 찾기·바꾸기로 처리하지 않음.

### 사례 12. 법정 기한과 기관의 기대

제40호 뉴질랜드 법률사무소 사고 기사는 법률상 `가능한 한 신속히` 통지할 의무와 감독기관이 기대하는 `인지 후 72시간`을 구별한다. 이를 `법정 72시간`으로 단순화하지 않는다. 인지 시점, 포렌식 결과와 통지 대상 판단, 외부 업체가 인지한 경우의 책임을 함께 설명해야 사건의 의미가 드러난다.

### 사례 13. 발의·검토·시행 구분

행정명령이 킬 스위치의 실현 가능성을 검토하고 권고안을 제출하라고 지시했다면 `킬 스위치 의무화`로 쓰지 않는다. 개정 법률의 세부 시행일을 정령에 맡겼다면 특정 날짜를 임의로 계산하지 않는다. 공포·발효·적용·유예가 서로 다르면 각각 명시한다.

### 사례 14. 민감한 데이터의 법률별 범주

그라인더 이용 사실이 성적 지향을 드러낼 수 있다는 판단은 데이터 흐름과 해당 기관의 법 해석에 근거해 설명한다. 이를 `앱 이용기록은 항상 민감정보`로 일반화하지 않는다. 일본 요배려 개인정보와 한국 민감정보, GDPR의 특별한 유형의 개인정보는 각각의 정의를 유지한다.

### 사례 15. 도구 출시와 표준 발표

덴마크 법규 가이드라면 기업 활동에 대한 질문 → 답변에 따른 적용 법률과 요건 안내 → 담당기관 지침 연결 → 기업의 최종 검토 책임이 남는 점을 설명한다. ETSI 데이터 품질 문서라면 지표의 수와 범주, 센서·인구통계 데이터에서 달라지는 중요 지표, 검증 도구와 활용 결과를 설명한다. `도구 공개`, `표준 발표`만으로 끝내지 않는다.

## 10. 실제 작업 순서와 검증

### 1단계: 전체 목록과 기준 판본 고정

작업실 API의 전체 목록을 받는다. 과거 표본 21건이나 임의의 79건으로 제한하지 않는다. `databaseAvailable=false`, 오래된 대체 데이터, 오류가 있으면 전체를 확보했다고 하지 않는다. 각 원고 ID, 현재 revision, 제목·본문·공식 URL과 비공개 수정본 존재를 확인한다.

### 2단계: 원문 전체와 연결 자료 읽기

기사마다 확인한 문서와 사실을 적는다. 가져온 HTML의 글자 수가 충분하다고 읽은 것으로 처리하지 않는다. 본문·첨부·판본·날짜·핵심 근거를 실제로 확인한다. 접근 실패한 원문은 별도로 표시하고 다른 공식 경로를 찾는다.

### 3단계: 정보 누락을 먼저 보완

문장 말끝을 바꾸기 전에 배경·행위·대상·판단·조건·시행·결과의 누락을 확인한다. 원문이 충분한데 얇은 원고는 원문부터 다시 구성한다. 기존 원고를 무조건 보존해 덧붙이는 방식도 피한다. 오류는 바로잡고 중복은 줄인다.

### 4단계: 문체와 흐름을 함께 윤문

제목부터 마지막 항목까지 한 편의 글로 읽는다. 요약 반복, 모호한 주어, 잘못된 인과관계, 장황한 명사 나열, 존댓말·평서형 혼용, 어색한 명사형을 고친다. 기사의 마지막을 기계적인 시사점으로 마감하지 않는다.

### 5단계: 원문과 역대조

날짜·금액·인원·기간·분모·시행 단계·처분 종류·법 조항·예외·의무 강도를 원문과 다시 대조한다. 문장이 매끄럽다는 이유로 의미가 정확하다고 판단하지 않는다. 위반 의혹과 확정 판단, 반출 미확인과 반출 부재를 구별한다.

### 6단계: 비공개 저장과 전 문장 재조회

스코프가 제한된 작업실 API를 사용한다. 수정 파일의 `report_id`, `base_revision`과 API의 `workspace_revision`을 보존·대조한다. 충돌 시 최신 원문과 제안을 비교해 실제 편집 내용을 다시 적용한다. revision 숫자만 바꾸지 않는다. 저장 응답 후 API를 다시 읽어 **수정한 모든 필드의 전체 문자열과 revision**이 일치하는지 확인한다. 저장은 발행이 아니다.

### 7단계: 실제 표시와 남은 쟁점 확인

화면에서 문단·줄바꿈·제목·요약이 정상적으로 보이는지 확인한다. 화면 확인이 API 검증을 대신하지 않으며, API 성공이 화면에서의 가독성을 보장하지도 않는다. 미확인 원문·근거 부족·메타데이터 오류는 구체적으로 보고하고 해결되지 않은 원고를 완성으로 계산하지 않는다.

## 11. 원고별 통과 기준

- 무엇이 새로 발생했는지 제목과 첫 항목에서 알 수 있다.
- 사건·정책을 이해하는 데 필요한 배경과 구체적 내용이 있다.
- 원문이 충분한데 두세 줄 공지 수준으로 끝나지 않는다.
- 세부 사실은 원문·연결 문서에서 확인했으며 없는 내용으로 분량을 채우지 않는다.
- 일반론을 지워도 기사에 충분한 정보가 남는다.
- 기관의 주장·권고·법원 판단·작성자의 해석이 구별된다.
- 개조식 보고서체가 자연스럽고 `했다/합니다/함`의 기계적 혼용이 없다.
- 소제목·고정 항목 수·새 기호 위계를 임의로 강제하지 않는다.
- 수치·기한·금액·예외·법적 단계·용어가 정확하다.
- 편집자용 지시와 검토 메모가 독자 본문에 섞이지 않는다.
- 같은 사건의 다른 기관 기사와 사실·용어가 충돌하지 않는다.
- 수정본 전체가 저장·재조회됐고 발행 여부를 혼동하지 않는다.

자동 검사는 누락·문장 형식·저장 오류를 찾는 보조 수단이다. 의미 검토와 원문 대조를 대신하지 않는다. 정규식 검사 통과를 `전수 윤문 완료`의 근거로 쓰지 않는다.

## 12. 다른 스레드에 전달할 작업 지시문

> 먼저 docs/trend-report-style.md와 docs/trend-reference-reading-notes.md, docs/translation/glossary.md 및 현재 작업실 연결 지침을 끝까지 읽으세요. 이 작업은 단순 요약이나 말끝 치환이 아니라 최근 1년 참고자료 수준의 해외 동향 원고 작성입니다. 전체 목록을 확인하고 원고마다 공식 원문과 연결 문서를 읽어 배경·행위·대상·판단·조건·수치·일정을 보완하세요. 원문이 충분한데 200~400자에 그치는 원고는 실질 누락을 다시 점검하세요. 단, 분량을 채우려고 내용을 창작하거나 일반론을 덧붙이지 마세요. 소제목과 새 기호 위계, 고정 3개 항목을 강제하지 마세요. 개조식 문체는 문장 전체의 응집성과 자연스러운 보고서체로 구현하고 법적 상태와 번역 용어를 보존하세요. 작성자가 확인할 사항은 독자 본문에 넣지 마세요. 비공개 수정본만 저장하고 모든 수정 필드와 revision을 다시 조회해 확인하세요. 실제로 읽고 수정한 범위와 미확인 사항만 정확히 보고하세요.

## 13. 자료·키·권한 관리

연결키와 DB 원고를 공개 저장소에 올리지 않는다. 작업실 캐시·수정본·원문 수집 기록은 무시되는 개인 작업 폴더에 보관한다. 이 지침과 비식별 검토 기록만 GitHub에 공유한다. 사용자가 업로드하지 않기로 한 참고 PDF를 임의로 공개하지 않는다. 지침을 읽었다는 이유로 발행·삭제·운영 DB 직접 수정 권한이 생기지 않는다.

이 지침은 수집기 구축 보고서나 동향 담당자 온보딩 README가 아니다. 출처 확대 제안과 작성 지침을 합치지 않는다. 사용자가 요청한 해외 기사 작성 품질을 일관되게 재현하기 위한 편집 기준이다.
